## 1. المقدمة (Introduction)

### 1.1 الغرض (Purpose)

تحدد وثيقة مواصفات متطلبات البرمجيات (SRS) المرجع الأساسي لمتطلبات نظام إدارة المدرسة (School Management System – SMS).

وتوضح حدود النظام، وبيئة تشغيله، وواجهاته الخارجية، والافتراضات المرتبطة به، والمراجع المعتمدة للمتطلبات التي سيُستند إليها خلال مراحل التصميم والتنفيذ والاختبار.

### 1.2 نطاق النظام (Scope)

سيدعم النظام العمليات الأكاديمية والإدارية والمالية لمدرسة أهلية واحدة.

يتكون النطاق الوظيفي المعتمد من الوحدات التالية:

1. إدارة الطلاب (Student Management).
2. إدارة المعلمين (Teacher Management).
3. إدارة الصفوف والشعب (Class Management).
4. إدارة الدرجات (Grade Management).
5. إدارة الرسوم الدراسية (Fee Management).
6. إدارة المستخدمين (User Management).
7. إدارة التقارير (Reports Management).

لا يشمل الإصدار الأول إدارة الحضور والغياب، والجداول الدراسية، والرواتب، والمكتبة، والنقل المدرسي، أو إدارة عدة مدارس.

## 2. الوصف العام للنظام (Overall System Description)

### 2.1 منظور المنتج (Product Perspective)

نظام إدارة المدرسة هو نظام معلومات مركزي يتيح الوصول عبر الويب، إلى جانب وظائف محددة من خلال تطبيق مكتبي.

ستستخدم الواجهتان خدمات تطبيق مشتركة وقاعدة بيانات علائقية مركزية للمحافظة على اتساق السجلات المؤسسية.

### 2.2 فئات المستخدمين (User Classes)

| فئة المستخدم | المسؤولية الأساسية |
|---|---|
| مدير المدرسة (School Principal) | الإشراف المؤسسي ومتابعة التقارير. |
| مدير النظام (System Administrator) | إدارة الحسابات والصلاحيات. |
| الموظفون الإداريون (Administrative Staff) | إدارة الطلاب والمعلمين والصفوف الدراسية. |
| المعلم (Teacher) | إدارة الدرجات الأكاديمية المصرح له بها. |
| المحاسب (Accountant) | إدارة الرسوم الدراسية والمدفوعات. |

يُعد الطلاب وأولياء الأمور مستفيدين غير مباشرين، ولن تكون لديهم حسابات مباشرة في الإصدار الأول.

### 2.3 بيئة التشغيل (Operating Environment)

| المكوّن | المتطلب |
|---|---|
| بيئة المستخدم (Client Environment) | أنظمة تشغيل مكتبية مدعومة ومتصفحات ويب حديثة. |
| بيئة التطبيق (Application Environment) | خدمات تطبيق مركزية. |
| تخزين البيانات (Data Storage) | قاعدة بيانات علائقية. |
| الشبكة (Network) | الشبكة المحلية للمدرسة (LAN). |
| الاتصال (Communication) | اتصال آمن بين العميل والخادم. |
| التطبيق المكتبي (Desktop Component) | متوافق مع منصة أجهزة العمل المختارة. |

سيتم تحديد التقنيات الدقيقة وإعدادات النشر خلال مرحلة تصميم النظام.

## 3. واجهات النظام (System Interfaces)

### 3.1 واجهات المستخدم (User Interfaces)

يجب أن يوفر النظام واجهات مناسبة لأدوار المستخدمين المصرح لهم.

ويجب أن تدعم الواجهات النصوص العربية، واتجاه العرض من اليمين إلى اليسار (RTL)، والتنقل المتسق، ورسائل التحقق الواضحة.

سيتم توثيق المواصفات التفصيلية للواجهات في المستند:

`../04-System-Design/Interface-Design.md`

### 3.2 الواجهات البرمجية (Software Interfaces)

| الواجهة | الوصف |
|---|---|
| عميل الويب ↔ خدمات التطبيق (Web Client ↔ Application Services) | اتصال آمن لتنفيذ العمليات المصرح بها. |
| العميل المكتبي ↔ خدمات التطبيق (Desktop Client ↔ Application Services) | وصول محكوم إلى وظائف التطبيق المشتركة. |
| خدمات التطبيق ↔ قاعدة البيانات (Application Services ↔ Database) | وصول مركزي إلى البيانات ومعالجة معاملات قاعدة البيانات. |

لا يُسمح بالوصول المباشر إلى قاعدة البيانات من تطبيقات المستخدمين ضمن البنية المعمارية المقصودة للنظام.

### 3.3 واجهات الأجهزة والشبكة (Hardware and Network Interfaces)

سيعمل النظام على أجهزة العمل المصرح لها داخل المدرسة والمتصلة بالشبكة المؤسسية.

ويجب تحديد سعة الخادم وإعدادات الشبكة ومواصفات أجهزة المستخدمين بناءً على متطلبات الأداء التي تم التحقق منها.

### 3.4 واجهات الأنظمة الخارجية (External System Interfaces)

لا يتضمن الإصدار الأول أي تكامل إلزامي مع أنظمة خارجية تابعة لجهات أخرى.

وأي عمليات تكامل مستقبلية ستتطلب تحليل متطلبات منفصلًا والحصول على الموافقة اللازمة.

## 6. متطلبات البيانات (Data Requirements)

### 6.1 كيانات البيانات الأساسية (Core Data Entities)

سيدير النظام كيانات المعلومات الرئيسية التالية:

| الكيان (Entity) | الوصف |
|---|---|
| الطالب (Student) | بيانات هوية الطالب ومعلومات التحاقه بالمدرسة. |
| المعلم (Teacher) | بيانات هوية المعلم ومعلوماته المهنية. |
| السنة الدراسية (Academic Year) | تعريف السنوات الدراسية. |
| الصف الدراسي (Grade Level) | تصنيف المراحل أو الصفوف التعليمية. |
| الشعبة الدراسية (Class Section) | تجميع الطلاب ضمن شعبة في سنة دراسية محددة. |
| المادة الدراسية (Subject) | المواد الأكاديمية المرتبطة بالصفوف الدراسية. |
| التكليف التدريسي (Teaching Assignment) | العلاقات بين المعلمين والمواد والشعب الدراسية. |
| القيد الدراسي (Enrollment) | توزيع الطلاب على الشعب وسجل التحاقهم وانتقالاتهم. |
| سجل الدرجات (Grade Record) | نتائج تقييم الطلاب. |
| هيكل الرسوم (Fee Structure) | تعريف الرسوم الدراسية المطبقة. |
| رسوم الطالب (Student Fee) | الرسوم المفروضة على كل طالب. |
| المدفوعات (Payment) | المعاملات المالية المسجلة. |
| حساب المستخدم (User Account) | معلومات تسجيل الدخول وإدارة الحسابات. |
| الدور (Role) | تصنيفات المستخدمين والصلاحيات المرتبطة بها. |
| سجل التدقيق (Audit Log) | سجلات العمليات الحساسة والأنشطة ذات الأهمية الأمنية. |

### 6.2 سلامة البيانات (Data Integrity)

يجب أن يحافظ النظام على التكامل المرجعي (Referential Integrity) بين السجلات المرتبطة، وأن يحتفظ بالمعلومات التاريخية عندما تتطلب قواعد العمل ذلك.

وسيتم تحديد العلاقات التفصيلية بين الكيانات وخصائصها وقيودها وقواعد تطبيع قاعدة البيانات (Normalization) في المستند:

`../04-System-Design/Database-Design.md`

## 7. القيود والافتراضات (Constraints and Assumptions)

### 7.1 القيود (Constraints)

- يدعم الإصدار الأول مدرسة واحدة فقط.
- يجب أن يعمل النظام ضمن البنية التحتية المتاحة للمؤسسة.
- يجب أن يخضع الوصول إلى المعلومات الحساسة لأدوار المستخدمين المصرح لهم.
- يجب المحافظة على نطاق الوظائف المعتمد والتحكم في أي تغييرات تطرأ عليه أثناء التطوير.
- يجب أن يحقق التنفيذ متطلبات الأمان وسلامة البيانات المحددة.

### 7.2 الافتراضات (Assumptions)

- سيشارك موظفو المدرسة المصرح لهم في مراجعة المتطلبات واختبارات قبول النظام.
- ستتوفر البيانات المؤسسية اللازمة لعملية الترحيل الأولية.
- ستوفر المدرسة اتصال الشبكة والبنية التحتية التشغيلية المناسبة.
- سيمتلك فريق التطوير المهارات والموارد المطلوبة للتقنيات المختارة.

## 8. التحقق من المتطلبات (Requirements Verification)

يجب تقييم كل متطلب باستخدام طريقة تحقق مناسبة.

| نوع المتطلب | طرق التحقق الأساسية |
|---|---|
| المتطلبات الوظيفية (Functional Requirements) | الاختبارات الوظيفية، واختبارات التكامل، واختبارات قبول المستخدم. |
| متطلبات الأداء (Performance Requirements) | اختبارات الحمل والأداء. |
| متطلبات الأمان (Security Requirements) | الاختبارات الأمنية ومراجعة الإعدادات. |
| متطلبات الموثوقية (Reliability Requirements) | اختبارات الفشل واستعادة التشغيل. |
| متطلبات سهولة الاستخدام (Usability Requirements) | اختبارات قبول المستخدم واختبارات الواجهات. |
| متطلبات البيانات (Data Requirements) | اختبارات قيود قاعدة البيانات وسلامة البيانات. |

يجب المحافظة على المعرفات المرجعية للمتطلبات طوال مراحل التطوير، لضمان إمكانية تتبع العلاقة بين المواصفات والتنفيذ وحالات الاختبار.

## 9. التحكم في تغييرات المتطلبات (Requirements Change Control)

يجب أن تخضع التغييرات التي تطرأ على المتطلبات المعتمدة لإجراءات منظمة تشمل:

1. تقديم طلب تغيير موثق (Change Request).
2. تقييم تأثير التغيير على نطاق المشروع والتكلفة والجدول الزمني وتصميم النظام.
3. الحصول على موافقة الجهة المخولة باتخاذ القرار.
4. تحديث المتطلبات والمستندات المرتبطة التي تأثرت بالتغيير.
5. تسجيل التغيير في سجل مراجعات المشروع (Revision History).

يجب المحافظة على معرفات المتطلبات ثابتة قدر الإمكان لضمان استمرارية التتبع.

## 10. القبول والاعتماد (Acceptance and Approval)

يُعد النظام جاهزًا للقبول عند استيفاء الشروط التالية:

- اجتياز جميع المتطلبات الوظيفية الإلزامية لاختبارات القبول الخاصة بها.
- تحقيق معايير القبول المطبقة على المتطلبات غير الوظيفية.
- عدم وجود ثغرات أمنية حرجة أو عالية الخطورة لم تُعالج.
- اجتياز الاختبارات المطلوبة لسلامة البيانات واستعادتها.
- إكمال ممثلي المدرسة المصرح لهم اختبارات قبول المستخدم (User Acceptance Testing).
- حصول النظام على موافقة مدير المدرسة لاستخدامه داخل المؤسسة.

## 11. الخاتمة (Conclusion)

تحدد وثيقة مواصفات متطلبات البرمجيات (SRS) حدود النظام، ومراجع المتطلبات، واحتياجات البيانات، والواجهات، والقيود، وشروط القبول الخاصة بنظام إدارة المدرسة.

وتشكل هذه الوثيقة، إلى جانب مستندات المتطلبات المشار إليها، الأساس المرجعي لمراحل تحليل النظام وتصميمه وتنفيذه واختباره.
