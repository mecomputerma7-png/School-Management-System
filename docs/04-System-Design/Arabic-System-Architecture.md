# نظام إدارة المدرسة
## معمارية النظام (System Architecture)

**إصدار المستند:** 1.0  
**التاريخ:** أكتوبر 2026  
**الحالة:** تصميم مقترح (Proposed Design)  
**نوع التطبيق:** تطبيق سطح مكتب (Desktop Application)

---

## 1. الغرض من المستند (Purpose)

يحدد هذا المستند المعمارية البرمجية المقترحة لنظام إدارة المدرسة (School Management System – SMS).

ويوضح التنظيم الهيكلي للنظام، ومكوناته الرئيسية، وآليات الاتصال بين هذه المكونات، وطريقة إدارة البيانات، ونموذج نشر النظام وتشغيله.

وتوفر هذه المعمارية أساسًا تقنيًا لتصميم قاعدة البيانات وواجهات المستخدم بصورة تفصيلية، وتنفيذ النظام واختباره.

## 2. نظرة عامة على المعمارية (Architectural Overview)

صُمم نظام إدارة المدرسة بوصفه تطبيق سطح مكتب (Desktop Application) مخصصًا لمدرسة أهلية واحدة.

تعتمد المعمارية المقترحة على **التصميم متعدد الطبقات (Layered Design)**، الذي يفصل المسؤوليات المتعلقة بواجهة المستخدم ومنطق الأعمال والوصول إلى البيانات.

يدعم النظام عدة مستخدمين مصرح لهم بالعمل من أجهزة الحاسوب الموجودة داخل المدرسة، والوصول إلى قاعدة بيانات علائقية مركزية من خلال الشبكة المحلية (Local Area Network – LAN).

### 2.1 المبادئ المعمارية (Architectural Principles)

تستند المعمارية إلى المبادئ التالية:

- **فصل المسؤوليات (Separation of Concerns):** تمتلك كل طبقة مسؤوليات واضحة ومحددة.
- **التقسيم إلى وحدات (Modularity):** تبقى الوحدات الوظيفية مستقلة منطقيًا، مع الاستفادة من الخدمات المشتركة.
- **الإدارة المركزية للبيانات (Centralized Data Management):** تُحفظ سجلات المدرسة في قاعدة بيانات مشتركة.
- **الأمان منذ مرحلة التصميم (Security by Design):** يُفرض التحقق من الهوية والتفويض والتدقيق على العمليات المحمية.
- **سلامة البيانات (Data Integrity):** تحمي قواعد العمل وقيود قاعدة البيانات المعلومات المؤسسية.
- **قابلية الصيانة (Maintainability):** يمكن تعديل المكونات مع تقليل تأثير التغييرات على الوظائف غير المرتبطة بها.

## 3. النموذج المعماري (Architecture Model)

يعتمد النظام **معمارية تطبيق سطح المكتب ثلاثية الطبقات (Three-Layer Desktop Architecture)**.

| الطبقة | المسؤولية |
|---|---|
| طبقة العرض (Presentation Layer) | توفير واجهات سطح المكتب ومعالجة تفاعلات المستخدم. |
| طبقة منطق الأعمال (Business Logic Layer) | تنفيذ عمليات التطبيق والقواعد المؤسسية وضوابط الوصول. |
| طبقة الوصول إلى البيانات (Data Access Layer) | إدارة الاتصال بقاعدة البيانات وعمليات حفظ البيانات واسترجاعها. |

تعمل الطبقات الثلاث داخل تطبيق سطح المكتب، بينما تُستضاف قاعدة البيانات العلائقية بصورة مركزية.

### 3.1 المعمارية المنطقية (Logical Architecture)

```text
+--------------------------------------------------+
|               Desktop Application                |
|                                                  |
|  +--------------------------------------------+  |
|  |           Presentation Layer               |  |
|  |        Forms / Views / Navigation          |  |
|  +---------------------+----------------------+  |
|                        |                         |
|                        v                         |
|  +--------------------------------------------+  |
|  |          Business Logic Layer              |  |
|  |     Modules / Rules / Authorization        |  |
|  +---------------------+----------------------+  |
|                        |                         |
|                        v                         |
|  +--------------------------------------------+  |
|  |             Data Access Layer              |  |
|  |      Repositories / Database Access        |  |
|  +---------------------+----------------------+  |
+------------------------+-------------------------+
                         |
                         | LAN / Database Connection
                         v
             +--------------------------+
             | Centralized Relational   |
             |        Database          |
             +--------------------------+
```

يمثل هذا النموذج التنظيم المنطقي للنظام المقترح، ولا يمثل اختيارًا نهائيًا للتقنيات التي ستُستخدم في التنفيذ (Technology Stack).

## 4. مكونات التطبيق (Application Components)

ينقسم التطبيق إلى سبع وحدات وظيفية، تدعمها مكونات بنية تحتية مشتركة.

### 4.1 الوحدات الوظيفية (Functional Modules)

| الوحدة | المسؤولية الأساسية |
|---|---|
| إدارة الطلاب (Student Management) | ملفات الطلاب وتسجيلهم ومعلومات التحاقهم. |
| إدارة المعلمين (Teacher Management) | سجلات المعلمين والتكليفات التدريسية. |
| إدارة الصفوف والشعب (Class Management) | الهياكل الأكاديمية والشعب الدراسية وتوزيع الطلاب عليها. |
| إدارة الدرجات (Grade Management) | إدخال الدرجات واحتسابها وتصحيحها واعتمادها نهائيًا. |
| إدارة الرسوم الدراسية (Fee Management) | هياكل الرسوم ومعالجة المدفوعات والأرصدة المالية. |
| إدارة المستخدمين (User Management) | حسابات المستخدمين والأدوار والصلاحيات وحالات الحسابات. |
| إدارة التقارير (Reports Management) | التقارير الأكاديمية والإدارية والمالية. |

تتواصل كل وحدة مع الخدمات المشتركة، وتصل إلى البيانات المحفوظة من خلال طبقة الوصول إلى البيانات (Data Access Layer).

### 4.2 المكونات المشتركة (Shared Components)

| المكوّن | المسؤولية |
|---|---|
| خدمة التحقق من الهوية (Authentication Service) | التحقق من بيانات اعتماد المستخدمين وإنشاء جلسات موثوقة. |
| خدمة التفويض (Authorization Service) | التحقق من الصلاحيات قبل تنفيذ العمليات المحمية. |
| خدمة التحقق من صحة البيانات (Validation Service) | تطبيق قيود الإدخال وقواعد العمل ذات الصلة. |
| خدمة التدقيق (Audit Service) | تسجيل العمليات الحساسة والتغييرات المهمة. |
| إدارة المعاملات (Transaction Management) | تنسيق عمليات قاعدة البيانات التي تتطلب تنفيذًا ذريًا (Atomic Execution). |
| خدمة التقارير (Reporting Service) | استرجاع بيانات التقارير المصرح بها وتجهيزها. |
| إدارة الإعدادات (Configuration Management) | إدارة إعدادات التطبيق والإعدادات المؤسسية. |

تمثل هذه المكونات مسؤوليات منطقية، ويمكن تنفيذها في صورة خدمات منفصلة أو مكونات داخلية ضمن التطبيق.

## 5. مسؤوليات الطبقات (Layer Responsibilities)

### 5.1 طبقة العرض (Presentation Layer)

توفر طبقة العرض واجهة المستخدم الرسومية لتطبيق سطح المكتب.

وتشمل مسؤولياتها:

- عرض نوافذ التطبيق ونماذجه وتقاريره.
- استقبال مدخلات المستخدم والتحقق الأولي من صحتها.
- عرض نتائج العمليات ورسائل الأخطاء.
- توفير التنقل بين وظائف النظام وفقًا للصلاحيات الممنوحة للمستخدم.

يجب ألا تنفذ طبقة العرض استعلامات قاعدة البيانات مباشرة، أو تطبق السياسات المؤسسية بصورة مستقلة عن طبقة منطق الأعمال.

### 5.2 طبقة منطق الأعمال (Business Logic Layer)

تنسق طبقة منطق الأعمال عمليات التطبيق وتطبق القواعد المؤسسية.

وتشمل مسؤولياتها:

- تنفيذ مسارات العمل الوظيفية.
- فرض قواعد العمل وقرارات التفويض.
- التحقق من العلاقات بين السجلات المؤسسية.
- احتساب النتائج الأكاديمية والأرصدة المالية.
- تنسيق المعاملات التي تشمل عدة سجلات مترابطة.

تُحدد قواعد العمل في المستند:

`../03-System-Analysis/Business-Rules.md`

### 5.3 طبقة الوصول إلى البيانات (Data Access Layer)

توفر طبقة الوصول إلى البيانات وصولًا منضبطًا إلى البيانات المحفوظة.

وتشمل مسؤولياتها:

- تنفيذ عمليات قاعدة البيانات.
- إدارة اتصالات قاعدة البيانات.
- ربط كيانات التطبيق بالسجلات المخزنة.
- دعم اتساق المعاملات.
- معالجة الاستثناءات المتعلقة بقاعدة البيانات.

يجب أن تستخدم عمليات قاعدة البيانات **الاستعلامات المعلَّمة (Parameterized Queries)** أو آليات مكافئة وآمنة للوصول إلى البيانات.

## 6. معمارية إدارة البيانات (Data Management Architecture)

يستخدم النظام قاعدة بيانات علائقية مركزية للحفاظ على اتساق السجلات المؤسسية بين أجهزة العمل المصرح لها.

### 6.1 تنظيم البيانات (Data Organization)

تدعم قاعدة البيانات مجالات البيانات المنطقية التالية:

| مجال البيانات | المحتويات الرئيسية |
|---|---|
| الطلاب (Students) | هويات الطلاب وسجلات الالتحاق. |
| المعلمون (Teachers) | ملفات المعلمين والتكليفات التدريسية. |
| الهيكل الأكاديمي (Academic Structure) | السنوات الدراسية والصفوف والمواد والشعب الدراسية. |
| الدرجات (Grades) | سجلات التقييم والنتائج الأكاديمية. |
| الشؤون المالية (Finance) | الرسوم الدراسية والمبالغ المستحقة والمدفوعات والتعديلات. |
| التحكم في الوصول (Access Control) | حسابات المستخدمين والأدوار والصلاحيات. |
| التدقيق (Auditing) | سجلات العمليات الأمنية والتغييرات الحساسة. |

سيُحدد التصميم الفعلي لمخطط قاعدة البيانات (Physical Database Schema) في مستند:

`Database-Design.md`

### 6.2 سلامة البيانات (Data Integrity)

يجب المحافظة على سلامة البيانات من خلال:

- قيود المفاتيح الأساسية والخارجية (Primary and Foreign Key Constraints).
- المعرفات الفريدة وقيود عدم التكرار المناسبة.
- التكامل المرجعي (Referential Integrity).
- العمليات القائمة على المعاملات (Transactional Operations).
- التحقق من قواعد العمل على مستوى التطبيق.
- التحكم في انتقال السجلات بين الحالات المختلفة.

يجب الاحتفاظ بالسجلات التاريخية وفقًا لسياسات الاحتفاظ بالبيانات وتصحيحها المعتمدة.

## 7. المعمارية الأمنية (Security Architecture)

تُطبق الضوابط الأمنية على مستوى التطبيق وقاعدة البيانات.

### 7.1 التحقق من الهوية (Authentication)

يجب أن يتحقق النظام من هوية المستخدم قبل السماح له بالوصول إلى الوظائف المحمية.

يجب التحقق من بيانات اعتماد المستخدمين باستخدام آليات مصادقة آمنة، ولا يجوز تخزين كلمات المرور بصيغة نصية صريحة (Plaintext).

### 7.2 التفويض (Authorization)

يستخدم النظام **التحكم في الوصول المستند إلى الأدوار (Role-Based Access Control – RBAC)**.

أدوار المستخدمين الخمسة الرئيسية هي:

1. مدير المدرسة (School Principal).
2. مدير النظام (System Administrator).
3. الموظفون الإداريون (Administrative Staff).
4. المعلم (Teacher).
5. المحاسب (Accountant).

يجب فرض الصلاحيات داخل طبقة منطق الأعمال، بدلًا من الاعتماد فقط على إخفاء عناصر واجهة المستخدم أو تعطيلها.

### 7.3 حماية قاعدة البيانات (Database Protection)

يجب أن يستخدم الاتصال بقاعدة البيانات بيانات اعتماد مخصصة للتطبيق ومحدودة الصلاحيات.

ولا يجوز تضمين إعدادات الاتصال الحساسة مباشرة داخل الشيفرة البرمجية (Hardcoding)، أو إظهارها من خلال واجهة المستخدم.

ويجب استخدام اتصال مشفر بقاعدة البيانات عندما تدعمه التقنية المختارة.

### 7.4 التدقيق (Auditing)

يجب أن يسجل النظام الأحداث المتعلقة بالأمان والتعديلات الحساسة وفقًا لمتطلبات التدقيق المعتمدة.

ويجب أن تحدد سجلات التدقيق المستخدم المسؤول والعملية المتأثرة ووقت حدوثها.

## 8. معمارية النشر والتشغيل (Deployment Architecture)

يعتمد نموذج النشر المقترح على عدة أجهزة سطح مكتب متصلة بخادم قاعدة بيانات مركزي عبر الشبكة المحلية للمدرسة.

### 8.1 مكونات النشر (Deployment Components)

| المكوّن | الوصف |
|---|---|
| أجهزة العمل (Desktop Workstations) | تشغيل تطبيق إدارة المدرسة للمستخدمين المصرح لهم. |
| الشبكة المحلية (Local Area Network) | ربط أجهزة التطبيق بخادم قاعدة البيانات. |
| خادم قاعدة البيانات (Database Server) | استضافة قاعدة البيانات العلائقية المركزية. |
| وحدة تخزين النسخ الاحتياطية (Backup Storage) | حفظ نسخ احتياطية محمية من قاعدة البيانات وفقًا لسياسة النسخ الاحتياطي المعتمدة. |

### 8.2 نموذج النشر (Deployment Model)

```text
+--------------------+      +--------------------+
| Administration PC  |      |    Teacher PC      |
| SMS Desktop App    |      | SMS Desktop App    |
+---------+----------+      +----------+---------+
          |                            |
          +-------------+--------------+
                        |
                        |
                    School LAN
                        |
          +-------------+--------------+
          |                            |
+---------+----------+      +----------+---------+
| Accountant PC      |      | Principal PC       |
```

يوضح المخطط المفهوم المقترح لنشر النظام وتشغيله.

وسيُحدد التكوين النهائي للشبكة ومواصفات البنية التحتية خلال التخطيط لمرحلة التنفيذ.

## 9. الاتصال وتدفق البيانات (Communication and Data Flow)

تتبع عمليات التطبيق تسلسلًا منضبطًا للتفاعل بين المكونات:

1. يبدأ المستخدم تنفيذ عملية من خلال واجهة تطبيق سطح المكتب.
2. تمرر طبقة العرض الطلب إلى طبقة منطق الأعمال.
3. تتحقق طبقة منطق الأعمال من صلاحية المستخدم والقواعد المطبقة على العملية.
4. تنفذ طبقة الوصول إلى البيانات العمليات المطلوبة على قاعدة البيانات.
5. تعود نتيجة التنفيذ عبر طبقة منطق الأعمال إلى طبقة العرض.
6. تعرض الواجهة نتيجة العملية للمستخدم.

يتصل تطبيق سطح المكتب بقاعدة البيانات المركزية من خلال الشبكة المحلية للمدرسة (LAN).

ويُمنع الوصول المباشر من طبقة العرض إلى قاعدة البيانات وفقًا للتصميم المنطقي للمعمارية.

## 10. الموثوقية والاستعادة (Reliability and Recovery)

يجب أن تدعم المعمارية الموثوقية التشغيلية من خلال:

- إدارة معاملات قاعدة البيانات (Database Transaction Management).
- المعالجة المنضبطة للأخطاء (Controlled Error Handling).
- إجراءات النسخ الاحتياطي المركزية (Centralized Backup Procedures).
- آليات استعادة قاعدة البيانات (Database Recovery Mechanisms).
- اكتشاف انقطاع الاتصال (Connection Failure Detection).
- المعالجة المتسقة للتعديلات المتزامنة على البيانات (Concurrent Data Modifications).

في حال عدم توفر الاتصال بقاعدة البيانات، يجب ألا تُعتبر العمليات التي تتطلب حفظ بيانات دائمة عمليات مكتملة بنجاح.

لا يشمل النطاق المعماري الحالي التشغيل دون اتصال (Offline Operation) أو مزامنة البيانات المحلية (Local Data Synchronization).

## 11. القرارات المعمارية (Architectural Decisions)

| معرف القرار | القرار | المبرر |
|---|---|---|
| AD-001 | اعتماد تطبيق سطح مكتب فقط (Desktop-only Application). | يتوافق مع نطاق المشروع الحالي. |
| AD-002 | اعتماد معمارية منطقية ثلاثية الطبقات (Three-Layer Architecture). | تفصل مسؤوليات الواجهة ومنطق الأعمال وحفظ البيانات. |
| AD-003 | اعتماد قاعدة بيانات علائقية مركزية (Centralized Relational Database). | تدعم مشاركة السجلات بصورة متسقة بين أجهزة المدرسة. |
| AD-004 | الاتصال بقاعدة البيانات عبر الشبكة المحلية (LAN). | يتيح التشغيل متعدد المستخدمين داخل المدرسة. |
| AD-005 | اعتماد التحكم في الوصول المستند إلى الأدوار (RBAC). | يقيد العمليات وفقًا للمسؤوليات المؤسسية. |
| AD-006 | تنظيم النظام في وحدات وظيفية مستقلة منطقيًا (Modular Organization). | يحسن قابلية الصيانة ويفصل مجالات العمل الرئيسية. |
| AD-007 | اعتماد استراتيجية نسخ احتياطي مركزية (Centralized Backup Strategy). | تدعم حماية البيانات المؤسسية واستعادتها. |

## 12. القرارات التقنية المعلقة (Technology Decisions Pending)

لا تزال تقنيات التنفيذ التالية بحاجة إلى تقييم واختيار.

| المجال | القرار المطلوب |
|---|---|
| لغة البرمجة (Programming Language) | اختيار لغة تطوير تطبيق سطح المكتب. |
| إطار واجهة سطح المكتب (Desktop UI Framework) | اختيار إطار العمل المستخدم لإنشاء الواجهة الرسومية. |
| نظام إدارة قاعدة البيانات (DBMS) | اختيار نظام إدارة قاعدة البيانات العلائقية. |
| تقنية الوصول إلى البيانات (Data Access Technology) | اختيار طريقة الاتصال بقاعدة البيانات وآلية حفظ البيانات واسترجاعها. |
| تقنية التقارير (Reporting Technology) | اختيار أدوات إنشاء التقارير وتصديرها. |
| التغليف والتثبيت (Packaging and Installation) | تحديد إجراءات توزيع التطبيق وتثبيته وتحديثه. |

يجب أن تراعي عملية اختيار التقنيات التوافق، وتعقيد التطوير، وقابلية الصيانة، والموارد المتاحة، ومتطلبات المشروع.

## 13. القيود المعمارية (Architectural Constraints)

تخضع المعمارية المقترحة للقيود التالية:

- يخدم النظام مدرسة واحدة فقط.
- يتم الوصول إلى وظائف التطبيق من خلال أجهزة سطح المكتب.
- يعتمد التشغيل الأولي على الشبكة المحلية للمدرسة.
- تُدار قاعدة البيانات بصورة مركزية.
- لا يشمل النظام إدارة عدة مدارس (Multi-School Operation).
- لا يشمل النظام تطبيقات الويب أو تطبيقات الهواتف المحمولة.
- لا يشمل النظام مزامنة البيانات أثناء العمل دون اتصال (Offline Synchronization).
- يجب حماية السجلات المؤسسية من الوصول غير المصرح به والتعديلات غير المتسقة.
